# Review 用户旅程验收门

当选中的中文设计文档包含用户旅程、前端产品体验、交互、可见状态或前端验收标准时，每位独立 reviewer 都执行本门禁。

## 1. 建立矩阵

先逐条提取方案要求，不按修改文件猜范围。至少映射：

- 主路径：用户从真实页面入口完成核心目标；
- 首次启动/空状态：无数据、无选中对象或尚未配置时入口仍有正确反馈；
- 正常状态：存在代表性数据时的点击、输入、保存、导航与刷新；
- 失败状态：方案要求的无效输入、权限、冲突、网络或服务错误；
- 持久状态：方案要求的刷新、重启、历史版本或运行固定；
- 适配状态：方案明确要求的键盘、窄屏/移动端或其他交互方式。

每行写清：设计文档与章节、前置状态、用户动作、预期可观察结果、验证方式和结果。

## 2. 真实执行

- 在实现 `exactSha` 的隔离本地环境或专用测试环境运行真实前后端；不得用另一提交、陈旧服务或生产数据代替。
- 从用户可见页面入口开始，实际执行点击、输入、选择、保存、导航、刷新及状态切换。直接调用 API 只能作为补充诊断，不能代替页面旅程。
- 优先运行已有端到端浏览器测试；缺少覆盖时使用可用的浏览器自动化逐步操作。保留命令、URL/视口、动作、实际结果及截图/测试产物等证据。
- 不得修改实现来帮助 Review 通过；发现问题只提交 finding。不得为复现而修改用户生产数据。

以下都不能单独证明用户旅程通过：构建成功、单元测试、组件/快照渲染、菜单文字存在、阅读 JSX、直接调用 API。

## 3. Fail closed

- 每位 reviewer 独立执行自己的矩阵；独立阶段不得复用或查看另一位 reviewer 的结论。
- 任一必需旅程失败，提交与方案章节绑定的 `plan_conformance` finding。
- 环境、权限或工具导致旅程无法执行时，提交“缺少真实用户旅程验收证据”的阻断 finding；不得 `approve`。
- 交叉检视逐位核对旅程覆盖。缺一位 reviewer、缺一个必需状态或只有静态证据，都不能进入通过共识。
- 共识阶段只有全部必需旅程在 `exactSha` 上取得真实交互通过证据时，才能设置 `checksPassed=true`。

## 4. F006 类设置功能最低覆盖

对设置、导航和 Workspace 相关功能，至少验证：

1. 零 Workspace / 首次启动；
2. 已选择 Workspace 的正常配置；
3. 无效 Draft、冲突或不可用状态的明确反馈；
4. 保存后刷新及方案要求的 Revision/Run 固定；
5. 方案明确要求的键盘与移动端路径。
